# 05 · 存量项目体检手册：4 维 20 项成熟度评分卡与诊断模板

当用户在存量项目中触发本 Skill 进行 **Review / Audit / 体检 / 评估增强**（即 `SKILL.md` 中的 **Mode B**）时，Agent 必须先使用工具扫描仓库代码，然后严格对照本手册进行打分、识别反模式、权衡项目阶段，并按标准格式输出诊断报告。

---

## 一、 4 维 20 项评测成熟度体检表（Audit Checklist）

请逐一核查目标代码库在以下 4 个维度的落实情况（每项标记 `✅ 已落实` / `⚠️ 部分落实` / `❌ 缺失` / `➖ 当前阶段免除`）：

### 维度 D1：边界切分与确定性单测（Boundary & Deterministic Tests）
- [ ] **D1.1 确定性逻辑剥离**：算分加权、等级判定、排期计算、数值容差比对是否已从 Prompt 中剥离为纯函数（如 `domain/`），且不采信模型自报的分数/结论？
- [ ] **D1.2 工具安全与防呆**：数学/财务计算、数据库查询等是否交由确定性工具执行，且工具内部不接受外部传入的越权参数（如 `user_id` 必须从服务端上下文注入）？
- [ ] **D1.3 脱机秒级单测**：日常单元测试（`pytest` / `vitest`）是否默认屏蔽了所有真实 LLM / Embedding 网络调用，做到零 Token 成本秒级运行？
- [ ] **D1.4 HTTP 请求体逐字节快照（Request Snapshot）**：是否有拦截底层 HTTP 传输层、对发往大模型的完整 JSON 请求体（含拼好的 System Prompt 与 Tool Schema）做逐字节比对的快照测试？
- [ ] **D1.5 零调用反向断言与漂移守卫**：前置护栏/限流/超额拦截单测是否断言了“大模型调用次数为 0”？是否有单测（Drift Guards）锁死“离线评测入口与线上 API 传给 Agent 的参数结构一致”？

### 维度 D2：数据集质量与场景覆盖（Dataset & Error Analysis）
- [ ] **D2.1 按职责拆分的专项套件**：评测集是否按 Agent 职责拆分为独立套件（如检索、判分、多轮辅导、摘要、记忆），而非混作一谈？
- [ ] **D2.2 受控扰动用例（Perturbation）**：判分/审核类数据集是否包含“全对（换解法）、部分对（单步错+错误传导）、全错（仅结论无过程）”的受控扰动样本，而非只有标准答案？
- [ ] **D2.3 反向红线用例（Reverse Cases）**：记忆写入、工具触发、话题护栏等模块是否配有专门的“绝不该触发/绝不该记”反向负例（含 Prompt 注入与隐私 PII），且设为 100% 必过门禁？
- [ ] **D2.4 检索双口径与跑题负例**：RAG 检索评测是否兼顾了“父子层级宽松口径”（防切块粒度错配假警报），并配有跑题负例来标定 Rerank 分数下限（搜不到返回空，不硬凑）？
- [ ] **D2.5 金标元数据与指纹锁**：每条用例是否记录了审核状态（`draft / approved`）与修订来源？加载数据集时是否计算 SHA256 内容指纹以防新旧考卷混比？

### 维度 D3：评估器与模型评委可信度（Evaluators & LLM-as-a-Judge）
- [ ] **D3.1 确定性规则评估器先行**：在调用昂贵的模型评委前，是否先用纯代码检查了 JSON 解析、篇幅行数、结论先行、草稿话泄漏（`draft_leak`）以及基于 Trace 白名单的虚构引用（`fabricated_citations`）？
- [ ] **D3.2 跨家族异构与全盲化**：模型评委是否使用了与被测模型不同的厂商家族？送审材料是否剥离了身份标签并使用盲号（Blind ID）？
- [ ] **D3.3 Pairwise 位置翻转与动态材料补齐**：两两对比是否按哈希确定性翻转了 A/B 顺序以抵消位置偏见？多轮对话中 Agent 动态调工具查出的内容是否完整补进了评委参考材料里？
- [ ] **D3.4 严重度强绑定（防老好人偏见）**：评委协议是否强制要求标注问题严重度（`severity: error | minor`），并由代码/脚本强制执行“有 `error` 则对应维度得分必须 $\le 3$ 分（不合格）”，且最终 `Pass / Fail` 由代码派生？
- [ ] **D3.5 盲种子防作弊与参照集校准**：全量评审是否混入了无标记的已知缺陷盲种子（Sentinel Seeds，检出率 $<80\%$ 告警）？是否有防重复评语/全满分水军的自检脚本？是否与人类或高阶参照集做过一致性校准？

### 维度 D4：运行门禁与线上质量飞轮（CI Gates & Production Flywheel）
- [ ] **D4.1 快慢分层与实验旋钮**：是否区分了日常调参用的快速档（`QUICK=1`，禁止晋升）与提交前的全量档？是否支持不改生产代码直接通过 `EXP=` 旋钮做 A/B 实验？
- [ ] **D4.2 手动晋升基线（防门槛下沉）**：基线更新是否必须经过人工确认并执行显式命令（`eval-promote`），且将阈值、基线、报告与代码改动放在同一个 Commit 提交？
- [ ] **D4.3 噪声标定与配置显式告警**：门禁容差（Tolerance）是否基于同配置多次运行的噪声标准差（$2\sigma$）设定？报告头部第一行是否显式打印实际生效的模型与 Thinking 模式并在偏离生产缺省时告警？
- [ ] **D4.4 三层可观测与防泄漏隔离**：本机评测是否有多重防线严防带正文的实验数据误推上云端？线上生产追踪是否做了严格的属性白名单脱敏与智能尾部采样（错误/慢请求/负反馈 100% 保留）？
- [ ] **D4.5 线上负反馈回流飞轮**：是否有明确的机制（SQL 分诊或自动化脚本）定期将线上用户点踩（👎）与人工改判（`self_grade <> auto_grade`）沉淀回金标数据集？

## 二、 8 大常见反模式排查表（Anti-Patterns）

在扫描代码时，重点揪出以下 8 种最容易让团队白费力气的反模式：

| 反模式名称 | 典型代码/工程症状 | 危害 | 标准药方 |
|---|---|---|---|
| **1. 把确定性逻辑全塞进 Prompt** | 让 LLM 直接输出最终加权总分、心算复利公式、自己判断意图路由 | 分数忽高忽低、算术频繁翻车、没法写单测 | 拆进 `domain/` 纯函数与 `calc` 工具；模型只判档位，代码算总分 |
| **2. 通配符打桩（Wildcard Mock）制造假绿** | 单测里 `mock("/api/*")` 或完全手写假 JSON，连 URL 拼成 `/api/api/` 都测不出来 | 测试 100% 全绿，线上真实链路一次都没通 | 打桩精确到完整路径；跨端 Fixture 用真实序列化产物；加 HTTP 请求体逐字节快照 |
| **3. 评测脚本与生产代码分叉** | `evals/` 脚本里自己拼了一套 System Prompt 和工具列表去调模型 | 线上早就改了第 5 版上下文，评测还在测第 1 版假系统 | 评测 Task 直接调生产用例函数，并加 Drift Guards 单测锁死入参一致 |
| **4. 迷信 1~5 分均值，放任“老好人评委”** | 让 LLM 评委直接打 1~5 分算平均分，评委在评语里写“算错了”却照样给 4 分 | 严重事实错误被 4 分均值掩盖，指标虚假繁荣 | 引入 `severity: error` 强绑定规则（有 error 必须 $\le 3$ 分），由代码派生二元 Pass/Fail |
| **5. 评委漏看工具动态返回材料** | 只把初始题干传给评委，漏传 Agent 在第 2 轮调检索工具拿回来的段落 | 评委把 Agent 合法引用的小节号冤枉成“编造出处” | 从 Trace 中提取本轮所有工具返回内容，动态拼入评委参考材料与引用白名单 |
| **6. 自动刷新基线导致门槛悄悄下沉** | 每次跑完评测自动覆盖 `baseline.json` | 每次改动退步 1%，十次迭代后退步 10% 却依然全绿 | 改为手动 `eval-promote`，且基线文件变更必须与代码改动同 Commit 提交 |
| **7. 不测噪声就为 0.1 分的波动折腾代码** | 单次评测掉了 0.15 分就立刻大改 Prompt，或者没看清成本翻了 3 倍 | 在评委随机噪声里无效内耗，或为微小提升付出数倍账单 | 同配置连跑 3 次测出 $2\sigma$ 噪声底数；在报告里把质量与成本/延迟并排算账 |
| **8. 环境变量串台把带正文的评测推上云端** | 本地跑评测时 SDK 自动读取了 `.env` 里的云端 APM Key，或默认 60s 超时重试 3 次 | 题库版权/用户隐私正文泄露上云；慢任务被静默重跑烧掉 3 倍钱 | 本地追踪强制绑定 `localhost` + 进程互斥防线；显式设 `timeout=900, retries=0` |

## 三、 务实工程权衡视角（Trade-off Lens — 拒绝教条主义）

在给存量项目写 Review 报告时，**切忌端出不食人间烟火的教条姿态**。必须先判断项目的团队规模与所处阶段，区分**“真正的工程漏洞”**与**“合理的阶段性取舍”**：

1. **关于金标样本量与章节覆盖度**：
   - 如果是一个人或小团队快速迭代的项目，金标只深度覆盖了最复杂、最核心的 1~2 个代表性模块（比如 15~20 条精雕细琢的用例），而没有铺满全量业务线——**这是非常聪明、务实的工程取舍（先跑通标准与卡口，再铺量）**。不要批评它“样本太少”，而应肯定其聚焦策略，并建议在扩量后用 $2\sigma$ 重标定容差
2. **关于缺乏人类领域专家（SME）**：
   - 很多独立开发者或初创团队请不起全职财会/法务/医疗专家逐条标金标。如果项目采用了**“确定性代码复算 + 跨厂商异构模型交叉审核 + 盲种子防作弊”**来替代人工抽检，应当高度肯定这套自洽的工程兜底机制，同时温和提醒：“在引入真人盲评抽检前，把评测分当作衡量改动前后相对趋势的信号，而非绝对达标背书”
3. **关于为什么不把全量 `make eval` 放进 GitHub Actions CI 自动跑**：
   - 全量模型评测动辄耗时 20~40 分钟且消耗真金白银的 API 额度。CI 只跑免费的 `make verify`（单测 + 请求快照 + 漂移守卫），而把 `make eval` 留在开发者本机提交前触发（甚至利用订阅制桌面端完成低成本评委打分），是极高性价比的务实决策
