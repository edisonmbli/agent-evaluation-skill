# 03 · 模型评委与校准：LLM-as-a-Judge 怎么建才可信

当评测开放式的回答质量（如多轮教学辅导、复杂方案生成、变式出题）时，代码正则无法独自完成语义评估，必须引入 **LLM-as-a-Judge（模型评委）**。但未受约束的模型评委天生带有“老好人偏见”“位置偏见”“啰嗦偏见”甚至会“偷懒套模板”。本指南规定了让模型评委真正可信的工程落地标准。

---

## 一、 确定性评估器先行：别把客观问题丢给主观评委

在调用模型评委之前，必须先跑一轮零成本、100% 稳定的确定性代码评估器（参考模板 [deterministic_metrics.py](../resources/deterministic_metrics.py)）：

1. **草稿话与思考过程泄漏检测（`draft_leak`）**
   - **痛点**：模型在关闭 Thinking 模式或连续调用工具后，常把内心独白拼进正文（如开头出现 `I'll verify the calculations...` 或正文中出现 `等一下，让我重新算一遍`、`这个数不对`）
   - **做法**：使用中英文草稿特征正则表达式直接扫描输出正文，命中即判 `draft_leak = 1.0`
2. **基于 Trace 白名单的虚构引用核对（`fabricated_citations`）**
   - **痛点**：模型在回答中引用文档小节号（如 `§3.2.1`）或关联题号（如 `第 48 题`），肉眼与普通评委很难分辨它是真查到了还是凭记忆瞎编的
   - **做法**：
     1) 从当前运行 Trace 中提取模型本轮**真正见过的所有材料**（系统注入的文档块、工具入参、工具返回结果），汇总出合法编号白名单集合 `seen_ids`
     2) 用正则提取模型回答中出现的所有编号，凡是不在 `seen_ids` 里的，直接由代码判定为虚构引用（`fabricated_citation_rate`）
     3) 将这份由代码生成的《编号核对清单》一并附入模型评委的案头材料中，防止评委把合法引用误判为编造，或放过真正的编造
3. **可读性与版式结构检查（`readability_scores`）**
   - 首段是否直接给出结论（不以“本题考查……”等废话起头，且含结论/等式线索）
   - 最长段落折算手机屏幕行数是否超限（如 $\le 6$ 行）
   - 包含等号与数字的长算式是否独立成行（未嵌在超过 60 字的句子中间）
   - 特定风格标识是否达标（如大白话风格下必须出现 `"打个比方"`，且 `"教材指出"` 全篇不超过 1 次）

## 二、 模型评委防偏见 6 大工程设计

### 1. 跨家族异构评审（Heterogeneous Family）
- **铁律**：绝不让同一个模型家族既当考生又当考官（同家族模型对自身生成风格有强烈的自我偏好 Self-Preference Bias）
- **配置**：例如被测业务模型用 `DeepSeek` / `Qwen`，评委模型必须换成 `Gemini` 或 `Claude Sonnet` / `GPT-4o`

### 2. 全盲化任务导出与目录物理隔离（Blind Masking）
- 导出待评任务时，文件名一律使用按内容哈希生成的盲号（如 `j-8f3a91c02b.md`）
- 剥离所有用例 ID、Prompt 版本号、`baseline / candidate` 身份标签；真实映射关系保存在评委无权读取的 `desk.map.json` 中
- 评委 Prompt 中明文严禁读取待评目录以外的任何仓库文件（防止评委去偷看基线报告或金标源文件）

### 3. 两两对比（Pairwise）按哈希确定性翻转位置
- 在做新版（Candidate）与旧版基线（Baseline）的 Pairwise 盲评对比时，评委天生存在倾向选 A 或选 B 的**位置偏见（Position Bias）**
- **做法**：根据 `sha256(f"{run_id}:{case_id}")[0] % 2 == 1` 将一半样本展示为 `[回答 A = 基线, 回答 B = 候选]`，另一半翻转展示为 `[回答 A = 候选, 回答 B = 基线]`，回收判定结果时再按映射表翻回真实胜负
- **注意样本量**：若同一条 Case 重复跑多次（`REPEAT=2`），方向是按 `case_id` 固定的，因此有效独立样本数是 Case 数而非总运行次数，样本较少时 Pairwise 波动较大（约 $\pm 0.3$），应与单点维度均分结合判断

### 4. 评委只给维度分，最终 `Pass / Fail` 由代码拍板
- **为什么不让评委直接报 Pass/Fail 或总分？** 评委自报的结论极易受整体印象干扰，且口径难以统一
- **做法**：
  - 若任务维度单一，直接要求评委输出二元判定 + 具体证据引用
  - 若需观察多维趋势（如 `correctness`、`grounded`、`structure`、`plain_language`、`focus` 五维 1~5 分），**回收代码一律忽略评委自报的任何通过结论**，严格由代码按硬规则派生：例如 `correctness >= 4 and all(other >= 3) and no_error_issues -> Pass`

### 5. 动态补齐多轮工具上下文，防止“冤假错案”
- 在多轮 Agent 评测中，Agent 往往会在第 2、3 轮自主调用检索或查询工具获取新信息
- **大坑预警**：如果组装给评委的参考材料里只放了初始静态文档，漏掉了 Agent 在对话中途调工具动态拿回来的文档片段，评委就会把 Agent 的合法引用冤枉成“无中生有/编造出处”！
- **做法**：必须从运行 Trace 中遍历所有 `execute_tool` Span 的返回值，动态拼接到评委材料的 `检索到的补充材料` 区块中

### 6. 解析失败单列告警，不混入质量分母
- 当评委模型自身偶发输出坏 JSON 或超时未完成时，标记为 `unjudged` 并在报告顶部单独高亮告警，**切勿将其当成被测 Agent 得 0 分计入分母**，以免扭曲真实质量均值

## 三、 两大杀手锏：治“老好人偏见”与治“偷懒套模板”

在 `CPALearning` 实战中，单纯写好 Rubric 依然会遇到两个致命问题：① 评委在评语里明明指出了事实计算错误，手底下却依然给 4 分及格（校准一致率仅 6/10）；② 评委为了省事，写脚本批量给几百份任务套用同一句满分评语。必须用以下两套硬机制封死：

### 1. 严重度强绑定规则（Severity-Score Binding — 专治老好人偏见）
在评委 Prompt（见 [judge_prompt_template.md](../resources/judge_prompt_template.md)）与自检脚本（见 [check_verdicts.py](../scripts/check_verdicts.py)）中立下硬规矩：
1. 评委在输出 `issues` 列表时，每一条问题必须包含：
   - `"dimension"`：归属的评分维度
   - `"severity"`：只能填 `"error"`（事实、数字、公式、术语错误，前后自相矛盾，编造出处，或与讲解要点 `key_points` 明确相悖）或 `"minor"`（不会误导用户的轻微措辞/排版瑕疵）
   - `"quote"` 与 `"reason"`：原文引用与具体原因
2. **硬性约束**：**凡是某个维度下存在 `"severity": "error"` 的问题，该维度的得分必须 $\le 3$ 分（严禁给 4 分或 5 分）！**
3. **实战效果**：加上这条规则并用脚本强制拦截后，Gemini 评委与 Claude 黄金参照集的 Pass/Fail 一致率直接从 **6/10 提升至 10/10**

### 2. 盲种子混入 + 整批防偷懒自检脚本（专治水军盖章与作弊）
1. **盲种子（Sentinel Seeds）**：
   - 准备 10 条已知存在典型缺陷的回答（由真实回答受控改错公式、数字、出处或结论生成，保存在评委不可见的独立目录中）
   - 每次全量评测时，随机抽 3 条盲种子混入待评队列，文件名格式与真实任务完全一致
   - 回收时统计盲种子检出率（被判 `Fail` 的比例）：**若检出率 $< 80\%$，报告立刻拉响高危告警，整批判定结果视为存疑不可信！**
2. **整批防偷懒自检（`scripts/check_verdicts.py`）**：
   - **评语查重**：若同一句 `rationale` 或 `reason` 在整批 $\ge 3$ 份判定文件中重复出现，直接报错打回（防止批量复制粘贴或写脚本生成）
   - **全满分比例上限**：当批次任务数 $\ge 20$ 时，若“所有维度全 5 分且 `issues` 为空”的比例超过 `40%`（或完全无问题的比例超过 `60%`），直接判定为敷衍盖章，整批打回重审

## 四、 评委校准（Calibration）与真实分数修正公式

每次更换评委模型版本或修改 Rubric 协议时，必须执行一次**评委校准**（并同步递增判定缓存版本号 `CACHE_EPOCH` 使旧缓存失效）：

### 1. 校准标准流程
1. 从真实运行记录中抽取 10~30 条有代表性的样本（覆盖好、中、差），由人类专家（或经背书的高阶参照模型如 Claude Opus/Sonnet）逐条打上黄金标签（`Pass = 1 / Fail = 0`）
2. 让待校准的评委模型独立评审同一批样本（混入全部盲种子）
3. 运行 [calibrate_judge.py](../scripts/calibrate_judge.py) 计算：
   - **盲种子检出率（Sentinel Recall）**：必须 $\ge 80\%$
   - **Pass/Fail 一致率（Agreement Rate）**：必须 $\ge 80\%$
   - **TPR（True Positive Rate，真阳率）**：黄金标签为 `Pass` 的样本中，评委也判 `Pass` 的比例
   - **TNR（True Negative Rate，真阴率）**：黄金标签为 `Fail` 的样本中，评委也判 `Fail` 的比例

### 2. 用 Rogan-Gladen 公式修正评委偏差
即使评委通过了校准，它的评分尺度仍可能比参照标准略松或略严。假设评委在全量评测集上测出的表面通过率为 $p$，已知该评委校准时的 $\text{TPR}$ 和 $\text{TNR}$（且满足 $\text{TPR} + \text{TNR} > 1$），则被测系统的**真实无偏通过率估计值 $\hat{\theta}$** 为：

$$\hat{\theta} = \text{clip}\left(\frac{p + \text{TNR} - 1}{\text{TPR} + \text{TNR} - 1},\ 0,\ 1\right)$$

- 直接调用 `python3 scripts/calibrate_judge.py` 即可自动完成 TPR、TNR、一致率、修正后真实通过率 $\hat{\theta}$ 及 Bootstrap 95% 置信区间的计算
- **工程纪律**：若评委在某些非核心维度上整体偏松（如比参照平均高 0.3~1.0 分），应在评测文档中明确记录各维度的平均分差，并遵循**“评委绝对分数看相对趋势，不跨评委比绝对值；更换评委必须先重评同一份基线输出再晋升”**的铁律
