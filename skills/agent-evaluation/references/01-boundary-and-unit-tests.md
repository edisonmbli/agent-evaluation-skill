# 01 · 边界切分与确定性单测：先分清代码单测与模型评测

在构建或审查任何 Agent 系统时，第一步永远是**划清“传统确定性代码测试（Unit / Contract Tests）”与“大模型评测（LLM Evals）”的职责边界**。如果把确定性代码 Bug 都留到慢且贵的端到端模型评测里去抓，评测体系很快就会因为高昂的 Token 账单、半小时起步的等待时间和随机波动而沦为摆设。

---

## 一、 职责切分矩阵：把核心逻辑从大模型手里剥离出来

在设计或重构 Agent 时，逐一审视业务链路上的每个动作，问一句：**“这件事有确定性答案吗？或者用户已经通过界面操作明确表达了意图吗？”**

| 业务动作 / 逻辑类型 | 该归谁管？ | 工程落地做法 | 怎么测？ |
|---|---|---|---|
| **意图路由（Intent Routing）** | 归确定性代码 | 前端按钮（如“讲透”“追问”“判分”“出变式题”）已表达明确意图，直接映射独立后端端点，不让 LLM 猜意图；只有开放追问才交给单个 Agent 自主调工具 | 路由契约单测 |
| **加权打分与等级判定** | 归确定性代码（`domain/`） | 模型只允许输出每个步骤的档位（如 `full / partial / miss`）与错因标签；总分加权、及格线判定、“错误传导不重复扣分”一律由纯函数计算，**直接忽略模型自报的分数** | 纯函数参数化单测（毫秒级） |
| **数学与财务公式计算** | 归确定性代码（`tools/`） | 严禁模型心算多位小数或查表；提供基于 AST 白名单的安全求值工具（如 `calc`），内置标准系数与统一四舍五入精度，语法错转成 `ModelRetry` 让模型重调 | 表达式求值边界单测 |
| **出题 / 代码生成结果校验** | 归双盲复算 + 代码比对 | 生成方（Generator）产出后，剥离答案与解析，只把题干交给独立校验方（Verifier）重做一遍；两边答案是否一致由代码按相对容差（如 `0.5%`）判定 | 容差比对与重试状态机单测 |
| **前置护栏与隐私清洗** | 归确定性代码（开流前） | 明显的 Prompt 注入、毫无歧义的跨界闲聊、手机号/邮箱等 PII 敏感信息、抄录原题干检查，一律用纯函数/正则在调模型前拦截返回 422 | 正反向规则单测 + 零调用断言 |
| **状态流转与排期算法** | 归确定性代码（`domain/`） | 复习排期（如 FSRS）、掌握度衰减、任务队列槽位分配全部收进纯函数，前后端严禁各写一份同名计算逻辑（防口径漂移，统一以服务端为准） | 确定性状态机与可控时钟单测 |
| **开放语义理解、多轮答疑、拆解步骤** | **归大模型（LLM）** | 模型真正不可替代的价值所在 | **走模型评测（`make eval`）** |

## 二、 守住“模型大门前的最后一米”：三大组装层锁死技术

把纯业务规则剥进 `domain/` 之后，最容易漏测的是**靠近大模型的那一层胶水代码**（Prompt 动态分段拼接、上下文预算截断、Tool Schema 挂载、以及评测入口本身）。为了在**不调真实大模型、零 Token 消耗**的前提下把这一层测稳，必须落地以下三项测试：

### 1. HTTP 请求体逐字节快照测试（Request Snapshot Testing）
- **解决什么痛点**：Agent 的 System Prompt 往往由七八个动态段落拼接而成，还要挂载多个工具的 JSON Schema。重构代码、调整上下文装配或升级 Agent 框架（如升级 Pydantic AI / LangChain 版本）时，极易在无意中打乱提示词顺序、破坏 Prompt Cache 前缀稳定性，或改变工具参数定义
- **落地方法**：
  1) 在最底层的 HTTP 传输层（如 Python `httpx.MockTransport` 或自定义 Wire 拦截器）截获 Agent 即将发往大模型 API 的完整 JSON Payload（包含 `model`、`messages`、`tools`、`temperature` 等全部字段）
  2) 将截获的 JSON 与版本库中预存的基线快照文件（`tests/fixtures/agent_requests/<scenario>.json`）做**逐字节比对**
  3) **纪律**：日常重构或升级依赖时，快照测试必须 100% 绿（证明行为逐字节不变）；只有有意修改提示词或工具定义时，才允许显式更新快照，并在 Commit 中说明原因

### 2. 拦截与拒绝逻辑的“零调用反向断言”（Negative Assertions）
- **解决什么痛点**：测试话题护栏、每日成本额度超限、未授权访问或参数非法时，如果单测只断言 `response.status_code == 422`，很可能代码实际上已经调完了大模型、花掉了钱，最后才在返回层报错
- **落地方法**：凡是测试拒绝类、拦截类、限流类逻辑，单测中必须同时包含三条反向断言：
  1) `assert llm_call_count == 0`（上游大模型调用次数为 0）
  2) `assert db_messages_written == 0`（未污染对话历史表）
  3) `assert usage_ledger_charged == 0`（未产生账本扣费）

### 3. 评测漂移守卫测试（Evaluation Drift Guards）
- **解决什么痛点**：很多团队在写离线评测脚本（`evals/`）时，自己在脚本里手拼了一套 Prompt 和参数去调模型。几个月后，线上 `/chat` 接口的上下文装配逻辑早改了，评测脚本还在测过时的假系统
- **落地方法**：
  1) **架构约束**：线上接口与离线评测必须调用**同一个上下文装配函数**（如 `build_deps()` / `run_Readonly_turn()`）
  2) **守卫单测**：编写专门的单测，直接构造相同输入，对比“线上 API 端点传给 Agent 的参数结构（`deps`、检索块、Thinking 开关、工具列表）”与“离线评测 Task 传给 Agent 的参数结构”逐项完全相等

## 三、 四层纵深防御体系与 8 种免调模型测试手法

在把请求真正发给昂贵的端到端评测前，完整的测试金字塔应按以下四层逐级过滤：

1. **L1 契约与 Schema 层（毫秒级，每次保存必跑）**：用 Pydantic `extra="forbid"`、`strict=True` 锁死工具入参、结构化输出模型与前后端 OpenAPI 契约；跨端测试的 Fixture 必须由后端真实序列化产物生成，严禁手写假 JSON
2. **L2 确定性单测与快照层（秒级，每次 Commit / CI 必跑）**：运行 `domain/` 纯函数单测 + HTTP 请求体快照测试 + 漂移守卫测试（如 `make verify`，配置 `pytest -m "not integration"` 默认物理断网）
3. **L3 录制回放与契约联调层（分钟级，升级外部依赖时跑）**：抓取线上或沙箱真实 API 响应做确定性回放，或跑一条零 Mock 的端到端冒烟链路
4. **L4 真实模型端到端评测（十几分钟，改 Prompt / 模型 / 检索参数时跑）**：调用真实大模型跑金标集（`make eval`）

### 附：8 种不调大模型就能拦下 70% 低级 Bug 的工程手法
1) **提取纯函数**：把正则清洗、JSON 后处理、分数加权、列表去重从 Agent 方法里拆成独立纯函数单测
2) **Schema 强约束与 `ModelRetry` 测试**：用假模型（如 `FunctionModel`）故意返回缺字段、越界枚举的坏 JSON，验证校验器能否精准触发重试并在重试耗尽时优雅降级（保留原文留痕、不写脏判定）
3) **时间锚定测试**：涉及“距离上次学习多久”“到期复习”等逻辑时，显式注入可控时钟（`now` 参数）并预置带历史时间戳的测试数据，严禁在业务代码里裸调系统当前时间
4) **跨模块真实产物交接测试**：上一步函数的真实输出直接作为下一步函数的输入，不居中打桩，专门抓字段名拼错、单位不一致等交接缝隙 Bug
5) **同步与网络故障注入测试**：针对离线缓存同步或外部工具调用，注入断网、`5xx`、`4xx` 以及“服务端已处理但响应在路上丢了”的故障，验证客户端重发时服务端能否靠幂等键（`client_id`）去重
6) **Prompt 前缀缓存稳定性测试**：断言同一对话线程内多次工具往返、或追加新消息时，System Prompt 的静态与半静态前缀逐字节不变（守护 1/50 价格的 Prompt Cache 命中率）
7) **工具定义体积上限测试**：模型收到的 Tool JSON Schema 往往比 System Prompt 还长；写一条单测统计各 Agent 挂载的工具 Schema 总字符数，卡死预算上限（防止无节制加工具撑爆上下文）
8) **多租户作用域强制测试**：静态扫描或运行时拦截，断言所有用户表查询必须经过统一的作用域包装器（如 `UserScope(user_id)` 同时激活数据库 RLS 与显式 `WHERE user_id = ?`），Agent 工具绝不接受外部传入的 `user_id` 参数
