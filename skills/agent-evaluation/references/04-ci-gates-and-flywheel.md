# 04 · 运行纪律、门禁与线上质量飞轮

评测集和评委搭好之后，如果缺乏严格的**运行纪律、基线门禁和线上回流闭环**，评测体系很快就会在几次紧急发版后烂尾。本指南规定了从日常本地迭代到线上持续监控的标准运转机制。

---

## 一、 评测分层运行：快速档看方向，全量档守大门

把所有评测做成铁板一块是导致“大家嫌慢不想跑”的头号原因。评测必须按耗时与成本分为三层：

| 层级 | 命令示例 | 跑什么 | 耗时 / 成本 | 什么时候跑 | 能否晋升基线？ |
|---|---|---|---|---|---|
| **L1 确定性验证** | `make verify` | 全量单测 + 请求体快照 + 漂移守卫 + `eval-check` | 秒级 / **\$0** | 每次保存、每次 Commit、CI 必跑 | — |
| **L2 快速档评测** | `make eval SUITE=tutor QUICK=1` | 仅跑各套件声明的 5~8 条核心代表性金标；不跑 Pairwise、不混盲种子 | 5~10 分钟 / 极低 | 日常调改 Prompt 期间快速看数字方向 | **严禁晋升**（`eval-promote` 直接拒绝） |
| **L3 全量档评测** | `make eval` | 全量金标 + 重复运行（`REPEAT=2~3`）+ Pairwise 对比 + 混入盲种子 | 20~40 分钟 / 约 \$0.3~\$1 | 改了 Prompt / 模型 / SDK / 工具上限 / 检索参数，**正式提交前必跑** | **允许晋升** |

## 二、 基线管理与数据集版本纪律（四大护栏）

### 1. 基线只能手动晋升（Manual Promote），绝不自动刷新
- **致命反模式**：每次跑完评测自动用最新分数覆盖 `baselines/` 和 `thresholds.toml`。这会导致每次微小退步都把门槛往下拉一点，几次迭代后门禁彻底失灵
- **正确做法**：
  1) `make eval` 只负责对比当前得分与 `evals/thresholds.toml` 中的 `baseline ± tolerance`，跌破容差即返回非零退出码阻断提交流程
  2) 只有开发者亲眼审查了报告与 Trace、确认“这次改动确实达到了期望的新水平（或属于有意识的成本/延迟交换）”，才手动执行 `make eval-promote RUN=<run_id>`
  3) **同 Commit 铁律**：手动晋升产生的 `thresholds.toml`、`baselines/`、`reports/` 变更，必须与对应的 Prompt / 代码改动放在**同一个 Git Commit** 里提交，让 Code Review 一眼看清“这次代码改动让指标从 A 变成了 B”
  4) **绝对底线锁死（`pinned = true`）**：对于绝不允许突破的红线指标（如 `parse_failure_rate <= 0.05`、反向记忆用例 `reverse_pass_rate >= 1.0`），在 `thresholds.toml` 中标记 `pinned = true`，任何 `promote` 操作只刷新 `baseline` 参考值，绝不改动 `floor / ceiling` 红线

### 2. “先改考卷，再改答题”（数据集 SHA256 指纹锁死）
- 金标数据集一旦发生任何增删改，新旧分数就失去了直接可比性
- **指纹机制**：使用 [dataset_fingerprint.py](../scripts/dataset_fingerprint.py) 对数据集的核心内容字段（剔除 `status`、`reviewed_by`、`author` 等人工审核元数据）计算 SHA256 指纹（如 `cpa.grading@626c8eb8`）
- **两步提交纪律**：
  - **Commit 1（改考卷）**：只修改或新增金标用例，**保持业务代码与 Prompt 一字不动**，跑一遍 `make eval` 并 `promote`（建立“新考卷上的旧系统基线”）
  - **Commit 2（改答题）**：修改 Prompt 或业务代码，再跑 `make eval` 与 Commit 1 的基线做公平对比

### 3. 在报告第一行显式打印环境与模型配置（防静默漂移）
- **实战教训**：开发者本地 `.env` 极易残留历史调试开关（例如本地残留了 `THINKING=0`，而线上生产默认是 `adaptive` 开启思考），导致本地跑了几十轮评测全是在测错误的配置
- **硬性机制**：评测流水线启动时，必须在终端首屏和 `report.md` 第一行醒目打印当前实际生效的 **Model 名称、Thinking 模式及开启/关闭回合计数、温度参数、数据集指纹、Git SHA**；一旦检测到与生产默认常量（`PROD_DEFAULT_*`）不一致，报告第一行直接输出 `⚠️ [HIGH RISK] 环境配置与生产缺省不一致` 告警

### 4. Rejudge（重评）必须清空旧书桌缓存
- 当修改了评委材料组装逻辑或评委 Rubric、需要对已跑完的某次运行重新送审（`make eval-rejudge RUN=...`）时，因为盲号是基于 `(run_id, case_id)` 确定性生成的，必须**先将旧批次判定归档清空**，并递增 `CACHE_EPOCH`；否则回收脚本会把旧判定当成新判定直接跳过，导致重评后数字纹丝不动

## 三、 非确定性波动标定与实验旋钮（`EXP=`）

### 1. 用 $2\sigma$ 法科学标定容差（Tolerance）
大模型输出与模型评委打分天然存在随机波动。门槛设太紧会天天误报狼来了，设太松则形同虚设：
1. **初始估算（小样本期）**：按“允许 1 个样本翻转”的量级设初始容差（如 12 条样本 $\times 3$ 次 = 36 次运行，单次翻转约 `0.03~0.08`，比率类容差设 `0.08~0.10`；1~5 分均值类容差设 `0.3`；确定性检索设 `0.03`）
2. **标准标定（样本稳定后）**：
   - 一行代码不改，用完全相同的配置连续跑 3 次全量评测（`LABEL=noise-1..3`）
   - 计算每个门禁指标在这 3 次运行中的样本标准差 $\sigma$
   - 将该指标的容差设为 $\text{tolerance} = \max(2\sigma,\ 1/N)$
3. **排障纪律**：当某次评测只有一个主观指标刚好跌出容差边界、其余指标全绿时，**先别急着改代码**，重跑一次（或 `eval-rejudge`）排除随机噪声；同时打开 `issues` 看一眼是不是真有偶发瑕疵（如草稿话泄漏）

### 2. 区分 `pass@k` 与 `pass^k`
- **`pass@k`（尝试 $k$ 次至少成功 1 次的概率）**：仅适用于“代码辅助生成供人挑选”“头脑风暴提供备选”等容许试错的场景
- **`pass^k`（连续运行 $k$ 次全部成功的概率）**：面向终端用户的客服、医疗、财税辅导、记忆写入等高可靠场景，必须看 `pass^k`（或多次重复的一致率 `verdict_stability`）。一条用例如果 3 次里有 1 次胡说八道，在线上用户眼里就是不可靠

### 3. 实验旋钮（`EXP=`）：不改生产代码做算账式 A/B
在评测 CLI 中支持通过命令行覆盖运行参数（如 `make eval SUITE=tutor EXP=tutor.thinking=false LABEL=no-thinking` 或 `EXP=model=deepseek-pro`），并严格执行白名单参数校验（拼错参数名直接报错，绝不静默忽略）。
- **怎么读 A/B 结果**：把质量指标（`pass_rate`、`correctness`）与代价指标（`cost_usd_per_case`、`latency_p50_s`、`tool_calls_mean`、`cache_hit_rate`）并排放在一张表里算总账
- **实战范例**：若实验显示全开 Thinking 让成本涨 3 倍、延迟涨 3 倍，但质量得分提升仅 `0.15`（完全在评委 `0.3` 的噪声范围内），则果断否决全开方案，改用按推理信号触发的“自适应 Thinking”

## 四、 三层可观测数据隔离：既要看得清，又绝不泄密与白烧钱

参考模板 [tracing_guard_template.py](../resources/tracing_guard_template.py)，将追踪与观测数据拆为职责分明的三层：

| 层级 | 存什么内容 | 采样策略 | 核心用途 |
|---|---|---|---|
| **1. 自有业务数据库（Postgres）** | **全量明细**：`usage_ledger`（每次调用的输入/输出/缓存命中 Token、峰谷真实花费、结局 `ok/error/cancelled`、`trace_id`）、`messages`（对话原文）、`attempts`（判分与人工复核）、`content_feedback`（👍/👎） | **100% 全量** | 成本额度管控、运营看板、按 `trace_id` 回查问题正文 |
| **2. 云端 APM（如 Phoenix Cloud / Langfuse Cloud）** | **严苛白名单脱敏（Scrubbed Spans）**：仅保留允许列表内的 ~15 个结构化字段（`agent.name`, `prompt.version`, `tokens.*`, `cost`, `error.code`, `thinking.reason` 等），**彻底抹除题干、Prompt、回答正文与异常堆栈文本** | **智能尾部采样**：报错、慢请求（>8s）、判分、用户点 👎、触发护栏 **100% 保留**；其余正常请求按 `10%~20%` 采样 | 监控线上错误分布、长尾延迟、各版本 Prompt 的负反馈率 |
| **3. 本机观测台（Local Phoenix）** | **带完整正文的离线实验**：包含完整 System Prompt、工具入参/出参、多轮回复与评委批注 | 离线评测 **100% 全量** | Compare 视图并排对比实验、点开 Span 树定位算错/搜错根因、人工标注校准 |

### 必须焊死的两个可观测防坑细节
1. **本机评测正文绝不进云端的三道防线**（配反向单测）：
   - 防线 1：离线评测追踪器只接受 `localhost` / `127.0.0.1` 端点，传入任何外部域名直接抛异常
   - 防线 2：自建独立的 `httpx.Client(base_url=localhost)`，彻底绕开 `.env` 环境变量里指向云端的 `PHOENIX_COLLECTOR_ENDPOINT` 和 `API_KEY`
   - 防线 3：进程内若检测到生产追踪器已初始化，直接拒绝挂载评测追踪器
2. **显式关掉评测框架的“超时静默重试”**：
   - 许多评测 SDK（如 `arize-phoenix-client` 的 `run_experiment`）默认 `timeout=60s, retries=3`。多轮 Agent 任务耗时常在 30~90 秒，一旦满 60 秒就会被框架掐断并在后台静默重跑 3 次，白白烧掉 3 倍 Token 账单！必须在代码中显式设为 `timeout=900, retries=0`

## 五、 线上质量飞轮：每周 30 分钟把线上故障变成回归金标

离线评测解决“已知题目不退步”，线上飞轮解决“真实用户遇到了什么没想到的新问题”：

1. **自动化前哨（每日定时重审）**：
   - 用户在界面对某条内容或回复点 👎 后，立即打标 `flagged`（暂停被其他上下文引用），由每日凌晨的定时任务调用免费/低成本模型 API 对照原文重审；重审不过或恢复后再次被点 👎 的，直接转入 `needs_human` 人工队列
2. **每周 30 分钟分诊例行（Triage Routine）**：
   - **拉取信号**：从数据库捞出过去 7 天的 ① 点 👎 回复（带原因分类：讲错了/没听懂/太长/跑题）；② **用户人工改判记录（`self_grade <> auto_grade`，这是价值最高的天然标注金标）**；③ 慢请求与解析失败记录
   - **四路分诊**：
     - 知识/公式讲错 $\rightarrow$ 补教材切片或修工具 $\rightarrow$ 沉淀为**辅导金标（带 `key_points`）**
     - 判分档位不准 $\rightarrow$ 修判分提示词 $\rightarrow$ 把用户真实作答与人工复核结果原样沉淀为**判分金标**
     - 引用了不相关章节 $\rightarrow$ 修知识点链接或切块 $\rightarrow$ 沉淀为**检索金标**
     - 篇幅太长/像念讲义 $\rightarrow$ 修风格规则或可读性评估器 $\rightarrow$ 沉淀为**大白话金标**
   - **验证闭环**：新金标入库后，**先用修改前的旧代码跑一次，确认新用例确实会 Fail（复现问题）**，再合入修复代码跑绿 `make eval`，形成永不回退的质量飞轮
   - **每周金丝雀巡检（Weekly Canary）**：每周哪怕一行代码没改，也定时跑一次核心判分/检索套件，第一时间抓出上游托管模型（如 `deepseek-flash` / `gpt-4o`）悄悄更新权重导致的模型漂移
